# Твоя миссия
Ты — научный сотрудник на борту научно-исследовательского корабля, потерпевшего крушение на неизвестной планете. Пока техники чинят двигатели, от тебя зависит спасение миссии.
Твоя задача — разработать единое веб-приложение, которое решит три ключевые научные задачи, стоящие перед экипажем. 
## Требования к решению
Тебе нужно создать веб-приложение, которое:
- запускает HTTP-сервер на порту 8000;
- предоставляет три API-эндпоинта (по одному для каждой задачи);
- принимает входные данные в формате JSON через POST-запросы;
- выполняет расчеты с учетом всех условий и ограничений;
- возвращает результаты в строго определенном JSON-формате.

Теперь перейдем к конкретным задачам. Каждая из них представляет отдельную научную проблему, которую необходимо решить для спасения экипажа.

# Задача 1: «Круиз Робинсона»
## Легенда
Корабль поврежден, но у нас есть аварийный шаттл, отчаянный агент Робинсон, готовый лететь за помощью, и мы как раз обнаружили планету, где мы сможем договориться о проведении спасательной экспедиции. Туда нам и надо отправиться. Проблема в том, что взлёт с нашей текущей планеты (назовем ее ```start_point```) требует чудовищных затрат топлива — настолько огромных, что каждый лишний килограмм на орбите стоит целого бака горючего.

Твоя задача – найти максимально оптимальный (по времени и топливу) путь до целевой планеты (назовем ее ```rescue_point```). 
P.s. запомни имена планет (начальной и целевой), они тебе пригодятся!
## Что мы знаем:
- на вывод единицы массы на орбиту нужно огромное количество топлива (считаем, что человек и баки с запасом кислорода массы не имеют);
- на борту ограничен запас воздуха — полет не может длиться вечно;
- после выхода на орбиту шаттл летит по автопрограмме:
  - половина имеющегося на борту топлива сразу тратится на разгон (с округлением до целых вниз);
    - при этом разгон принудительно прекращается, если при сжигании очередной единицы топлива будет пройдено больше половины от всего запланированного расстояния;
    - пока разгон не завершен, выполнять гравитационные маневры нельзя (но можно просто перемещаться по ребрам графа)
  - затем шаттл летит по инерции (равномерное движение без ускорений); при этом можно заложить в программу выполнение одного или нескольких гравитационных маневров, на которые будет тратиться время и топливо;
  - при приближении к цели оставшаяся часть топлива тратится на полное торможение шаттла, т.е. полет должен закончиться с нулевой скоростью
    - учитывай, что если мы взяли гравитационный разгон, то тормозить, соответственно, придется дольше; аналогично разгону, в процессе торможения никакие маневры выполнять нельзя;
  - работа двигателей на разгон и торможение осуществляется таким образом, что каждую секунду сжигается одна единица топлива:
    - учитывай, что чем меньше на борту топлива, тем меньше суммарная масса шаттла, следовательно, тем большее ускорение получит шаттл;
    - считай, что расход единицы топлива происходит мгновенно, после чего на одну секунду шаттл получает соответствующее его текущей (без учета только что потраченного топлива) массе ускорение;
    - на последней секунде торможения двигатели могут работать меньше секунды, чтобы не придать шаттлу скорость в обратном направлении; при этом все равно тратится полная единица топлива и ровно секунда на выполнение торможения (оставшееся время шаттл неподвижен).
    
## Гравитационный маневр
Вместо прямого полета можно использовать систему космических тел (звезд, планет и лун) для гравитационных маневров. Каждый маневр дает прирост скорости, но требует точного расчета траектории и затрат топлива на коррекцию курса.

Система космических тел образует ориентированный граф, в котором узлы - это звезды и планеты, а ребра - допустимые прямые перелеты между телами. Движение возможно только по ребрам графа (нельзя произвольно менять курс).

Параметры каждого тела:
- уникальный идентификатор;
- масса тела (в условных единицах);
- список допустимых радиусов маневра (в условных единицах).

Параметры каждого ребра:
- идентификаторы начального и конечного тел;
- расстояние между телами (метры).

Механика гравитационного маневра заключается в следующем:
- при пролете вокруг космического тела шаттл разгоняется на определенную величину, зависящую от таких параметров как, например, радиус облета; соответственно, для каждого тела может быть спланировано несколько различных маневров, но выполнить при пролете мимо тела можно только один;
- появляется дополнительный расход топлива на коррекцию траектории;
- затрачивается дополнительное время на выполнение маневра.

## Что нужно сделать в этой задаче
Написать код, который:
- определит, возможно ли преодолеть найденный путь с имеющимися ресурсами (запасами топлива и воздуха);
- найдет путь в графе космических тел между заданной парой звезд, при котором суммарное время полета будет минимально возможным в условиях ограниченности запасов топлива;
- для каждого тела на пути выберет оптимальный гравитационный маневр. При этом допустимо пролететь мимо тела и не выполнять гравитационный маневр (простое перемещение по графу, затраты времени и топлива на корректировку курса к следующему телу в таком случае считать нулевыми).

## API-интерфейс задачи
Все три задания в рамках Проектного этапа должны составлять **ОДНО** веб-приложение. Приложение должно запускать HTTP-сервер на порту 8000 и обрабатывать запрос (для задачи 1): ```POST /api/v1/robinson_cruise```

Формат запроса (JSON):
```json
{
  "mass_shuttle": 1000.0,
  "mass_fuel_unit": 1.0,
  "power_per_unit": 1000.0,
  "oxygen_time": 864000,
  "total_fuel": 7000,
  "fuel_consumption": 3.0,
  "bodies": [
    {
      "id": "planet1",
      "gravity_assists": [
        {
          "velocity_gain": 10000.0,
          "fuel_consumption": 40,
          "time_to_execute": 1095
        },
        {
          "velocity_gain": 24000.0,
          "fuel_consumption": 84,
          "time_to_execute": 2026
        }
      ]
    },
    {
      "id": "gas_giant",
      "gravity_assists": []
    }
  ],
  "edges": [
    {
      "from": "start_point",
      "to": "planet1",
      "distance": 2e8
    },
    {
      "from": "planet1",
      "to": "gas_giant",
      "distance": 1e5
    },
    {
      "from": "gas_giant",
      "to": "rescue_point",
      "distance": 4e6
    }
  ]
}
```
Формат ответа (JSON):
```json
{
  "can_reach": true,
  "min_flight_time": 709698.8,
  "route": ["start_point", "planet1", "gas_giant", "rescue_point"]
}
```
Код ответа: ```200 OK```

Формат ответа, если не можем долететь:
```json
{
  "can_reach": false
}
```
Код ответа: ```200 OK```

Формат ответа при вводе некорректного формата или диапазона значений (JSON): 
```json
{
  "status": "incorrect_input"
}
```
Код ответа: ```400 Bad Request```

Где:
- ```mass_shuttle``` — масса шаттла без топлива (кг);
- ```mass_fuel_unit``` — масса единицы топлива (кг);
- ```power_per_unit``` — ускорение, прилагаемое к единице массы за счет расхода одной единицы топлива (кг*м/с²);
- ```oxygen_time``` — время, на которое хватит воздуха (секунды, целое число);
- ```total_fuel``` — общий доступный запас топлива (целые ед.);
- ```fuel_consumption``` — расход топлива – сколько единиц топлива сжигается за вывод единицы массы на орбиту при взлете;
- ```bodies``` – космические тела, _0 <= len(bodies) <= 100_:
  - ```id``` — уникальный идентификатор тела (строка);
  - ```gravity_assists``` — описание допустимых гравитационных маневров: для выполнения маневра потребуется `time_to_execute` секунд и `fuel_consumption` единиц топлива, а прирост скорости составит `velocity_gain` м/с;
  - конечные точки маршрута (start_point и rescue_point) в списке bodies не указываются, для них отсутствуют варианты грав. маневров;
- ```edges``` – ребра:
  - ```from``` — идентификатор начального тела;
  - ```to``` — идентификатор конечного тела;
  - ```distance``` — расстояние между телами (метры);
  - в списке ребер должны хотя бы по одному разу упоминаться стартовая и конечная вершины;
- ```can_reach``` — можем долететь или нет (булевое значение);
- ```route``` — последовательность имен космических тел в выбранном пути, начиная со входной и заканчивая выходной;
- ```min_flight_time``` — общее время полета (в секундах, одна цифра после запятой);
- ```status``` — статус ответа приложения. 

Учитывай, что важной частью решения задачи является проверка валидности входных данных. В числе возможных ошибок может быть как несоблюдение описанного выше формата (например, отсутствие или неправильное наименование части полей, ошибки в типах данных), так и некорректность значений (например, выход за допустимые диапазоны, нарушение связности данных или несоответствие условиям задачи).  
Автоматическая проверка включает не только тесты на корректную обработку валидных запросов, но и тесты на некорректные входные данные.  
Решение должно корректно обрабатывать такие случаи и возвращать ответ строго в указанном формате.

За решение этой задачи можно получить максимум **25** баллов.

# Задача 2: «Гори, гори, моя звезда»
## Легенда
Корабль пытается установить стабильную связь с удаленной звездой, которая передает критически важные данные для спасения миссии. Однако сигнал передается очень медленно и требует непрерывного приема в течение длительного времени. 

Проблема: в системе существует сложная иерархия небесных тел (планеты и их спутники), которые постоянно заслоняют собой звезду. Мы не можем позволить себе потерять ни секунды передачи – любой перерыв сделает полученные данные бесполезными. 

Передача данных возможна только при условии прямой видимости звезды на протяжении всего сеанса связи. Твоя задача – найти ближайший временной промежуток, пригодный для передачи, определить момент его наступления и продолжительность. Если таких окон нет — сообщить об этом. Более того, отправка сообщений автоматизируется бортовым компьютером, и потому начать отправку возможно только в начале каждой секунды (т.е., например, можно начать сеанс связи ровно в момент времени `12:40:55`, без милли- или микросекунд на таймере).

## Что мы знаем:
- мы находимся в фиксированной точке наблюдения (точка 0,0 на плоскости) на планете ```Atlas```;
- интересующая нас звезда находится очень далеко — считаем ее материальной точкой;
- вокруг планеты, на которой мы находимся, (вокруг 0,0) располагаются небесные тела – звезды, планеты и луны, образующие иерархическую структуру:
  - звезды неподвижны;
  - планеты вращаются вокруг звезд (движение по круговой орбите);
  - луны вращаются вокруг планет (движение по круговой орбите);
- все небесные тела — это идеальные сферы определенного радиуса, которые могут заслонять нужную нам звезду;
- сама планета, на которой мы находимся, звезду не заслоняет, однако луны (указываются в списке небесных тел с ```parent_id: "Atlas"```), вращающиеся вокруг нее, могут перекрывать нужную нам звезду.

## Звездная система
Особенности, которые стоит учитывать:
- у нас многоуровневая система – тела движутся по сложным траекториям с учетом иерархии;
- сигнал требует непрерывного приема в течение времени `required_transmission_time`;
- мы начинаем наблюдать в момент start_observation_time.

## Что нужно сделать в этой задаче
Написать код, который:
- смоделирует движение всех тел в иерархической системе;
- определит моменты, когда луч от наблюдателя к звезде пересекает какое-либо тело;
- найдет интервалы времени, когда звезда полностью видна;
- найдет ближайший к началу наблюдения интервал длиной не менее ```required_transmission_time```;

Например, мы начинаем наблюдение за звездой в момент времени 0 и нам необходимо 100 секунд для передачи сигнала, а ближайшие два затмения занимают следующие временные интервалы: `[35.1, 74.2]`, `[180.5, 197.8]`, то ближайшим подходящим нам интервалом будет `[75, 180)`, т.е. придется подождать 75 секунд, а сам интервал будет иметь длину 105.

# Задача 3: «Звездочетность»
## Легенда

Корабль потерял ориентацию в пространстве. Чтобы определить свое местоположение в галактике и построить обратный курс, нужно найти на небе знакомое созвездие — тот самый астронавигационный маркер, по которому можно сориентироваться.

Проблема в том, что мы не знаем, в какой части галактики находимся, и поэтому созвездие, которое мы ищем, может быть произвольным образом искажено в пространстве. Полагаться на визуальное сходство нельзя — нужно найти похожую по структуре конфигурацию звезд.

Под похожей конфигурацией пары созвездий мы будем понимать совпадение сразу двух свойств графов, которые задают созвездия:
- графы должны быть изоморфны друг другу;
- мы должны определить взаимно-однозначное соответствие между вершинами (звездами) первого и второго созвездий, и для этого потребуется проанализировать длины ребер: они могут отличаться в силу пространственных искажений, однако относительный порядок сохраняется. 

Например, мы наблюдаем структуру `a - (10) - b - (20) - c` на первом графе и `x - (5) - y - (50) - z` на втором (в скобках обозначены длины ребер). Мы понимаем, что эти два графа изоморфны друг другу, а по относительной величине ребер (ребро `xy` меньше ребра `yz`, как и ребро `ab` меньше, чем `bc`) можно сделать вывод, что мы можем сопоставить звезды так: `a->x`, `b->y`, `c->z`.

## Что мы знаем
Нам повезло! Местные жители предоставили доступ к своему звездному справочнику (Star Catalog). В нем для каждой видимой звезды записаны:
- ее уникальное местное имя (строка);
- координаты (x, y, z) в системе координат данной планеты.

Но имена в справочнике совершенно незнакомые, а координаты привязаны к этой планете, поэтому напрямую сопоставить их с нашими картами нельзя. Однако мы знаем, что местные жители строят созвездия по единым общегалактическим правилам:
1. Звезды делятся на группы (созвездия) по пространственной близости, а именно: группой считается компонента связности неориентированного графа, рёбра которого проведены между звездами, находящимися на расстоянии, не превышающем заданное значение D (параметр `max_neighbor_distance`).
Фактически это означает, что созвездие является максимальным по включению подмножеством звезд, между любыми двумя вершинами из которого существует маршрут, причем ни одно расстояние между парой звезд в маршруте не превышает D.

2. В созвездии должно быть не меньше `min_size` и не больше `max_size` звёзд. 
Одиночные звезды, а также слишком маленькие или слишком большие скопления созвездиями не считаются.

3. Сама схема созвездия (какие звезды соединены линиями) строится как минимальное остовное дерево (MST) на множестве его звёзд.
Сумма длин ребер в этом дереве минимальна, циклы отсутствуют.
Гарантируется, что для каждого созвездия минимальное остовное дерево единственно (все попарные расстояния между звездами одной группы различны).

## Что нужно сделать в этой задаче
Написать код, который:
- кластеризует звезды по правилу связности с порогом D и отбирает только группы, чей размер попадает в интервал [`min_size`, `max_size`]; полученные группы считаются наблюдаемыми созвездиями;
- для каждого такого созвездия восстанавливает его схему — минимальное остовное дерево, используя евклидовы расстояния между звёздами;
- сравнивает схемы всех найденных созвездий с заданным графом целевого созвездия на схожесть структуры (изоморфизм и соответствие звезд по длинам ребер);
- если ровно одно созвездие на небе оказалось похожим на целевое, возвращает список имен звезд, соответствующих вершинам целевого графа (в порядке вершин 0…n-1); в противном случае (ни одного или несколько совпадений) возвращает ```found: false```.

### Docker Compose со ссылкой на образ в GitVerse Registry

Тебе необходимо самостоятельно собрать образ своего решения, опубликовать его в GitVerse Registry, а затем указать ссылку на этот образ в файле ```docker-compose.yml```.

Для этого тебе необходимо:
- авторизоваться в GitVerse Registry;
- собрать docker-образ;
- запушить собранный образ в GitVerse Registry;
- в корне репозитория создать файл ```docker-compose.yml``` с этим образом;
- проверить работоспособность compose-файла.

Важно: перед сдачей решения проверь, что:
- все файлы (```instruction.md```, ```Dockerfile```, ```docker-compose.yml```) находятся в корне репозитория;
- образ в GitVerse Registry доступен.

Файл ```docker-compose.yml``` должен содержать описание **ровно одного сервиса** — сервиса с твоим приложением.
